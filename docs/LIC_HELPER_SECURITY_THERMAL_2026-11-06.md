# LIC-helper 2.1 — security, privacy, CPU and first-flight correctness

Date: 2026-11-06. Experimental branch; requires testing on device and against an actually restricted network.

## Confirmed Xray fragmentation bug corrected

FinalMask `maxSplit` counts pieces, **not split points**. A value of `1` sent one original TLS record and made the previous "two packets" profile ineffective.
* `lic-duet`, `lic-duet-gate`, `lic-duet-mss`: now `maxSplit=2` (two TLS records after one split).
* `lic-trio`: now `maxSplit=3` (three TLS records).
* Unit tests explicitly assert the real configuration generated by `XrayConfigCompiler`, matching upstream Xray semantics.
* Fragmented TLS records do not guarantee separately observed physical TCP segments. No real/fake TCP packet injection is claimed.

Source: https://github.com/XTLS/Xray-core/blob/main/transport/internet/finalmask/fragment/conn.go

## Two additional *implemented* client-side transport strategies

* **LIC-FirstWrite** (`lic-first-write`): stream-first-write slicing with `packets="1"`, two pieces (112–160 B initial size) and a 3–5 ms gap. Unlike TLS-record surgery, this alters the first TCP write's byte-stream layout without touching its contents. This is a true transport option, not a changed uTLS label.
* **LIC-FirstBurst** (`lic-first-burst`): applies bounded slicing to the first **two** write operations (`packets="1-2"`), each at most two pieces, with 1–3 ms gap.

Both use Xray's documented FinalMask `fragment` mode. They are optional/experimental; FirstWrite is in the automatic recovery shortlist and both are selectable in the explicit Workbench. They do not alter the REALITY key, UUID, SNI, shortId or Vision flow.

## Reduced unnecessary CPU work

* A successful encrypted HTTPS/REALITY profile is reused. No hidden startup benchmark or 512-KiB stream download.
* At most **five** protected first-flight candidates and **two** stock-REALITY candidates. The stock alternative is strictly the last resort after helper profiles. No unencrypted/direct fallback.
* Native Xray startup, local SOCKS, invalid configuration or user-cancel failures are **terminal**. The previous adaptive retry handler incorrectly treated some local/core exceptions as DPI failures, potentially restarting Xray multiple times, generating heat and hiding the actual error.
* Only failed authenticated egress validation allows changing the REALITY profile. Timeouts are retried only when known to come from an outbound egress check.
* The foreground status ticker is now at most every two seconds during operations, every five seconds when idle. No background polling is added. Network interface monitoring for native libbox remains event-driven.

## Privacy/security hardening

* Existing subscription storage remains AES-256-GCM in Android Keystore; no plaintext tokens/URLs in prefs or logs; app backup, device transfer and cleartext HTTP remain blocked.
* Subscription mutation operations are synchronized in-process to avoid overlapping read/modify/write operations. **Cross-process locking is not yet implemented**; Android AtomicFile still guarantees atomic individual writes.
* Vault clear now also wipes the per-install salted REALITY strategy cache and last cross-process status trace.
* Physical-network type cache no longer incorrectly categorizes a VPN TUN as a mobile or Wi-Fi link. Only a coarse, unambiguous physical network category is kept, never SSID, ICCID, IP, carrier or target domain.
* Invalid per-app routing entries are no longer printed with package names and full exceptions in logcat.
* The existing subscription downloader uses HTTPS only, forbids redirects to internal IPs and refuses private DNS responses. Android's `VpnService` still excludes the VPN app's own UID to avoid recursion; **an explicitly approved subscription refresh may use the physical connection**. This remains a disclosed limitation rather than a claimed leak-free tunnel.

## Important remaining limits

* **Not a Zapret2 raw-packet port:** real/fake desynchronization, forged TTL/SEQ, overlapping TCP packets, and packet checksum tricks require a trustworthy packet backend or approved raw-socket/root capability. Nothing like that is falsely advertised as present.
* No claim of complete immunity to carrier DPI or zero phone heating. These modifications reduce avoidable work, but radio and SoC power must be measured on hardware.
* Android's per-device **Always-on VPN + Block connections without VPN** is the recommended privacy control while disconnected. The app does not silently enable Android lockdown for the user.
* Merge only after Android device tests, IPv4/IPv6 DNS leak assessment, warm/cold start, VPN network switch and measured thermal/battery validation.
