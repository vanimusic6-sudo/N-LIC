## Scope and reproducibility

- Repository baseline: `master` at `08f77cee2a391008650814a4a64fe3d48c5d9552`.
- Android upstream: `romanvht/ByeByeDPI`; bundled native ByeDPI submodule: `hufrea/byedpi@ba532298de7b28cfe854aea83d061369d13ca290`.
- Bundled hev-socks5-tunnel: `heiher/hev-socks5-tunnel@4d6c334dbfb68a79d1970c2744e62d09f71df12f`.
- Scope: static source inspection and pure-Kotlin decision tests. No claim of network-level DPI bypass, battery improvement, or complete Android APK verification until CI and device experiments run.

## How this stack works

1. Android's `VpnService` creates a TUN interface (in VPN mode).
2. `hev-socks5-tunnel` forwards traffic from that interface to a local SOCKS proxy.
3. `ByeDPI` owns outbound connections and applies selected TCP/TLS/HTTP or UDP transformations.
4. The Android app builds command arguments, manages the worker process, and runs HTTP probes to compare strategies.

This is not a remote VPN. It does not encrypt otherwise-unencrypted traffic or hide the user's public IP. Evasion effectiveness depends on the DPI and the protocol.

The native engine supports targeted techniques including TCP splitting (`--split`), out-of-order delivery (`--disorder`), TCP urgent/OOB data (`--oob`, `--disoob`), fake data with constrained TTL (`--fake`, `--ttl`), and TLS-record splitting (`--tlsrec`). `--auto` can switch to later groups based on detected failures, which is more sensible than applying an expensive combination indiscriminately.

## Confirmed application-layer defects (baseline)

| Priority | Component | What the source showed | Phase 1 change |
| --- | --- | --- | --- |
| P0 measurement | `SiteCheckUtils.checkSiteAccess` | HTTP status is ignored when counting success: a fully-read HTTP 403, 451, 500, or a response with unknown Content-Length could count as successful. | Count only 2xx with readable body, or explicit 204/205; classify outcomes independently for testing. |
| P1 resource use | `SiteCheckUtils` | For large Content-Length, the test read the entire body for every strategy/request. | Read a 4 KiB sample instead of downloading the full body. |
| P1 reliability | `TestService.stopEngine` | An unconditional `while(true)` retried shutdown forever, potentially freezing strategy selection after native worker problems. | Bound shutdown to 8 seconds, then attempt forced abort. |
| P2 imported settings | `TestService.loadSettings` | Imported numeric values bypass the UI validators; strategy placeholder substitution did not escape quotes. | Bound request/timeout/concurrency counts and escape inserted SNI. |

### Caveats remaining after these fixes

- The two half-delays in the strategy loop are intentional (warm-up and cooldown); they remain unchanged.
- An HTTP 200 block page can still look reachable. The metric is **HTTP reachability**, not definitive proof of unblocking. A content signature/known-good reference or service-specific endpoint is needed to confirm content correctness.
- A perfectly valid HTTP 200 with zero bytes is conservatively marked as unverified, which can create false negatives for deliberately empty endpoints.
- A `Host`/TLS/DNS/QUIC failure can be conflated if only one endpoint is tested. This is why controlled baselines and separate metrics are necessary.

## Additional risk and compatibility questions to verify

1. **IPv6 route coverage:** `ByeDpiVpnService.createTunnel` adds an IPv6 TUN address and `::/0` route only if `ipv6_enable=true`; otherwise IPv6 may travel outside the app's VPN route, depending on device and lockdown policy. Treat this as a potential routing bypass, not a demonstrated information leak. Test with a dual-stack endpoint on actual hardware.
2. **DNS provenance:** the app configures a DNS server for the VPN; ByeDPI's native domain resolution still uses `getaddrinfo`. Capture DNS outcomes and distinguish routing problems from DPI interventions.
3. **Local proxy exposure:** ByeDPI defaults to listening on all interfaces unless the Android configuration explicitly injects loopback. The Android default is `127.0.0.1`; a manually configured public/wildcard address may expose a no-auth proxy on the LAN.
4. **Import/privacy surface:** the manifest declares broad storage access; backup is enabled with effectively empty backup rules. Assess removal of broad file permissions on devices with a system document picker and explicitly define backup expectations.
5. **Native baseline:** upstream `hufrea/byedpi` has 9 commits after the pinned `ba53229`, including fixes for HTTP CONNECT target parsing, file-descriptor exhaustion, and response timeouts. Do not upgrade the submodule without an isolated ABI/build check and traffic regression tests.
6. **UDP and QUIC:** UDP fake packets are not equivalent to full HTTP/3 or VPN-protocol support. First establish which protocols and paths are actually used before composing strategies.

## Experiment protocol for phase 2

A reproducible test should record network type (Wi-Fi/cellular), IPv4/IPv6, destination, protocol, command hash, first-byte latency, HTTP/TLS result, error category, and number of attempts. Avoid logging user payloads, full URLs with tokens, or user identifiers. Use user-controlled test hosts or public endpoints explicitly intended for health checks.

For every candidate strategy, compare:

1. No-proxy control (detect whether there is actually a block).
2. Local proxy with transformations disabled (detect tunnel/proxy defects).
3. One technique at a time (split, disorder, OOB, TLS record split, controlled fake) on TLS/HTTP.
4. A small adaptive chain driven by measured failure classes; no blind large combinations on every new connection.

Use multiple runs and compare both success rate and latency/battery cost. Refuse to declare a win solely because one HTTPS request returned HTTP 200.
