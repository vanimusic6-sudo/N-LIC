# N-LIC · LIC-helper 2.0 first-flight transport (2026-11-06)

Status: experimental, implementation on top of PR #31. No observed success on a blocked carrier yet.

## User-facing contract

* The main LIC-Assist/LIC-helper switch is the only automatic opt-in.
* ON: **every compatible VLESS + TCP (RAW) + REALITY VPN attempt** starts with a non-stock first-flight profile. There is **no diagnostic pre-scan** asking whether assistance is required.
* Every candidate is authenticated against the unchanged REALITY node and checked via HTTPS *only to determine whether a connection works*, not to choose whether to enable LIC-helper.
* If the first profile fails, try a small finite collection of real Xray first-flight options on that same node. **Only after all helper variants fail** may unmodified REALITY be tried. Never connect directly to the public Internet as a fallback.
* OFF: pass through the imported REALITY parameters unchanged.
* The switch never resets to OFF on failure. A successful fallback is reported explicitly, rather than represented as a helper success.
* A per-node, coarse-network, 12h cache remembers an actually working fingerprint/transport pair. An old cached STOCK result cannot prevent helper from being applied while the switch is ON.
* Optional **user-triggered** Workbench can compare profiles; startup does not run its 28-test matrix or the hidden 512 KiB streaming diagnostic.
* User-set REALITY fingerprint remains pinned on the first attempt; all REALITY authentication material (UUID, serverName, public key, shortId, Vision flow) is untouched.

## Actual capabilities delivered

All items below are Xray v26.10.31 client-side settings on the physical REALITY outbound, not merely UI labels.

| ID | Technique | Xray effect |
|----|-----------|-------------|
| `lic-duet` | **LIC-Duet** | FinalMask `tlshello` fragmentation with **maxSplit=1**, one split into two TLS records, first fragment 160–220 bytes, delay 3–5 ms |
| `lic-duet-gate` | **LIC-Duet Gate** | One early split (48–80 B), delay 7–11 ms; alternative first-flight footprint |
| `lic-duet-mss` | **LIC-Duet Frame** | The two-record profile plus `sockopt.tcpMaxSeg=1200`. Refuses an imported conflicting MSS setting |
| `lic-trio` | **LIC-Trio** | FinalMask `tlshello`, `maxSplit=2`; bounded three-record variant |
| `split-soft`, `split-early`, `split-zero` | Existing FinalMask profiles | Previously implemented alternatives |
| `mss1200`, `mss900`, `tfo-off`, `idle-keepalive` | Existing socket-level strategies | Kept for explicit Workbench; some are stability settings, not DPI desynchronization |

The runtime starts with the previously successful helper profile or Duet; then considers Gate, Duet Frame, split-soft, baseline Duet. Only then it tries stock REALITY with known compatible uTLS fingerprints. Candidate count is bounded to nine.

No inserted random bytes, TCP checksum corruption, forged QUIC, or unsafe manipulation of encrypted REALITY payload.

## Two packets: important distinction from Zapret2

**Implemented:** two TLS records/fragments within *one valid, authenticated REALITY TCP connection*. A nonzero gap makes separate socket writes more likely, but **it does not guarantee two physical TCP segments**. Observe the real wire with an authorized capture to verify segmentation.

**Not implemented:** Zapret2 `fake`/`fakedsplit`, TTL-limited forged TCP segments, TCP sequence overlaps, alternate real/fake packet images and selective routing of forged segments. These require packet-level control and sufficiently predictable kernel/network handling. Generic rootless Android Xray sockets and `VpnService` do not provide a trustworthy portable interface for the equivalent semantics. Claiming otherwise would be misleading; it could also break unrelated VPN transport and REALITY authentication.

**Potential future native work (not shipped):**
* A strictly isolated controlled-packet backend with explicit device capability detection, not an unconditional fallback to raw sockets.
* Packet-scope correctness tests (IP/TCP checksums, sequence windows, SACK/retransmission, IPv4 vs IPv6, MTU/TCP MSS) on rooted/authorized test devices before exposing any real/fake mechanism.
* A PCAP-based audit comparing source ClientHello, TLS-record boundaries and *actual observed* TCP segments.
* Separate network-specific verification before claiming that any countermeasure defeats a particular DPI.

## Validation to run before merge

1. Unit tests: Duet has `maxSplit=1`; Trio has `maxSplit=2`; Frame combines MSS 1200 and FinalMask; private REALITY credentials unchanged.
2. Preference test: ON + no cache starts with Duet, NOT STOCK; an old STOCK cache cannot disable it; stock is placed after all helper trials.
3. Forced imported uTLS must not be silently replaced by Chrome.
4. Device tests: one nonblocked network; one actually restricted network; both Wi-Fi/mobile and IPv4/IPv6 where available. Track initial HTTPS, end-to-end TUN, first render/stream and battery.
5. Network capture: two TLS records are not automatically two TCP packets.
6. Verify that failed helper profiles close the previous Xray instance before reusing its SOCKS endpoint. Verify successful fallback doesn't toggle the user switch OFF.
7. Rootless Android crash/leak regression, plus manual security review of DNS/VPN routing.
